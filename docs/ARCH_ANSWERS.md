# 架构设计题回答

> 5 个模块，每个模块选 1 道题。以下每题用连续段落回答，不分点。

## 一、Context / Performance

### Q2：一个 session 连续聊了 200 轮，context 快爆了，你会怎么做压缩？如何确保压缩后的对话仍然流畅？

我不会按“轮数”来压，而是按 token 预算分层压，因为 200 轮里真正占空间的通常不是用户说的话，而是工具结果、重复的 system prompt 和历史叙述。压缩的第一原则是保住“目标、硬约束、用户偏好、当前待办和最近几轮原文”，其次才是删掉旧过程。具体做法是先做成本最低的工具结果预算，把单个超长结果截到头尾并保留全文到 artifacts，再做旧轮次的微压缩，最后才把更早的轮次交给模型生成结构化摘要；原始旧消息同时写入 transcript，需要细节时可以回查。这样大部分情况下花的是字符串操作的钱，只有确实不够时才花一次模型调用。

摘要本身要有固定 schema，至少包含目标、硬约束、已确认事实、已完成、未完成、重要工具结论和下一步，而不是一段自由散文。压缩只在用户轮次边界触发，不能切在工具调用链中间，否则 `tool_use` 和 `tool_result` 会失去配对；摘要放在 system prompt 的独立小节，不插入 messages，避免连续 user 消息和角色错乱。最近六轮原文永远保留，当前用户消息绝不改写，todo 每轮重新注入，这样追问时模型仍然接得上。压缩后我会用“当前目标是什么、有哪些约束、上一步做了什么”做一次连续性检查，而不是只看摘要是否通顺。

代价是摘要会丢细节，而且摘要调用本身也花钱、会破坏前缀缓存，所以压缩应该设缓存热度门，利用率不高时不要压。边界在于法律、医疗、合同这类逐字约束场景不能只靠摘要，必须保留原文引用或外部检索；200 轮的真实效果也要看约束保留率、追问正确率和压缩前后成本，不能只用“摘要看起来不错”来验收。一句话，压缩的本质不是删旧消息，而是按信息价值分层：目标和约束不能丢，工具结果可以预算，旧过程可以摘要，原文要能回查。

## 二、Memory

### Q1：和聊天 Agent 熟悉半个月后，用户问了一个以前问过的问题，Agent 如何做 memory 召回更合理？

我会把 memory 设计成项目级、文件化、模型参与写入的系统：把记忆分成用户偏好、反馈、项目、外部资料四类，每条记忆一个 Markdown 文件，带 YAML frontmatter，用一个索引文件做目录，路径按当前工作目录的哈希放在项目目录下。模型不是被动等着 runtime 写记忆，而是通过 prompt 里的 memory 说明，自己写记忆文件；召回时让模型从索引里挑相关记忆，再异步预取，把结果注入最后一条 user message；新鲜度则结合文件时间和索引提示。这个设计的好处是记忆可读、可编辑、可审查，缺点是项目级作用域、模型直接写文件、语义筛选和异步预取都带来不确定性和额外调用。

半个月后用户问一个以前问过的问题，我会沿用这个分层和召回思路，但把作用域从 project 改成 user：按用户存，否则同一个工作目录下不同用户会混在一起。写入上，从通用 write_file 改成受限的 memory 工具 save/search/list，再加上运行时对“记住”“以后都”“我喜欢”“我的某某是”的显式捕获作为兜底；写入前做去重、冲突检测、来源和置信度记录，先不做完整的 LLM 抽取和合并，避免引入过多不确定性。这样既保留模型主动记的优点，又避免把通用写文件权限暴露给模型。

召回上，让模型做语义筛选并异步预取，再注入最后一条 user message，召回更强，但每轮多一次模型调用、多一层异步状态和不确定性；本题先用关键词、时间衰减和类型权重，把结果放在 system prompt 的独立小节，带类型、日期、来源，并写明“记忆可能过时，当前指令优先”。如果记忆成为核心卖点，再把语义筛选、向量召回和 Markdown 主存储加索引补回来；当前是 JSON canonical 加只读 Markdown 镜像，兼顾结构化操作和可读性。边界在于记忆会过时、冲突、被错误写入，所以要有 supersede、可删除、必要时人工确认，评估看 recall@k、回答正确率和错误记忆率，而不是只看能不能翻出旧话。

## 三、Task

### Q1：对于长程任务，大模型执行一段时间可能会忘掉目标，你知道哪些解决方案？各有什么优缺？

目标遗忘的本质不是模型“不够努力”，而是上下文衰减加上自我评估失真：早期约束被挤出窗口，模型又倾向于相信自己“已经做完”。所以核心解法不是反复在 prompt 里写“别忘了目标”，而是把目标外置成可检查的状态，包括目标契约、可勾选的 todo、每一步的 progress ledger，以及关键节点的 checkpoint。每轮开始都把当前目标、硬约束、当前 todo 和上一步进展重新注入，让模型在一个稳定的小状态上工作，而不是依赖它记住几十轮前的话。

在此基础上，要用独立审计来对抗“自说自话”。执行者说“做完了”不算数，Auditor 只读验证环境是否真的改变，完成必须过机器可校验的门禁，例如状态、完整性、契约审计三行同时满足；证据必须来自环境，不能只来自执行者的自述。子任务可以用全新上下文，避免错误滚雪球，但结果要通过 artifacts、progress 或文件传递，不能只留在子 Agent 的脑子里。对于开放式任务，还要把“完成”写成可验证的验收条件，否则门禁本身就没有意义。

代价是审计会增加成本、延迟和实现复杂度，门禁过严还会导致任务永远完不成，所以要有两个反向约束：Manager 不能把自己临时加的谨慎变成新的阻塞要求，Auditor 也不能因为缺少完整记录就无限怀疑。边界在于有些任务的完成标准本身模糊，或者证据已经不可观察；这时应该承认残余风险、前瞻性埋点，而不是为了证明过去而要求重做。一种常见的治理思路是把角色拆成 Manager、Executor、Auditor，并把完成变成外部可验证的事实；本质上就是把“目标”和“完成”从模型的自我叙述里拿出来。

## 四、Tool / Session Runtime

### Q2：如果 session state 为 busy，此时用户又发来新消息，或者异步工具完成事件也到达，runtime 应该如何处理？

我会把 session 做成单写者状态机加事件队列，而不是让多个 loop 并发写同一份历史。状态大致在 idle、running_llm、running_tool、waiting_async、cancelling 之间转换，所有事件都进同一个有序队列，由唯一的写者串行处理；这样用户消息、模型响应、异步工具完成和取消事件不会交错破坏状态。busy 时用户又发消息，默认不应该直接打断当前模型调用，而是先入队并给用户一个确认；在模型返回后、工具调用之间、工具结果回填后这些安全点，再决定是排队执行、注入为补充指令，还是按用户的明确“停止”取消当前任务。

异步工具完成事件必须带 `session_id` 和 `tool_call_id`，先查 pending 表，匹配上了才接收；重复事件要幂等丢弃，session 还在忙就入同一队列，当前步结束后再处理，session 已经取消就把结果标记为 stale，存下来但不回灌上下文。每个事件要有单调序号，状态转换要有版本号或乐观锁，所有写操作幂等，事件日志和 pending 工具表要能支撑重启恢复。队列还要有上限、背压和超时，不能让一个迟迟不返回的异步工具把 session 永远卡在 busy。

代价是队列会带来延迟，安全点注入和取消会让状态机变复杂，尤其是取消时要处理已经产生的副作用，例如已经发出的请求或已经写入的文件。边界在于单机内存队列只能解决单进程问题，多实例部署需要分布式锁或按 session 路由到唯一写者；异步结果也可能晚到很久，所以要有超时和“稍后通知”的产品设计。一句话，busy 不是拒绝新事件，而是把事件放进同一个有序队列，由单写者在安全点串行决策，异步完成也必须带 id、幂等、可恢复。

## 五、Runtime 对比

### Q1：Claude Code 的工具输出方式和国内 GLM / 豆包等 OpenAI-compatible function calling 有什么不同？各自优缺点？

Anthropic 和 Claude Code 把工具调用与结果做成结构化的 content block：assistant 消息里是 `tool_use`，user 消息里回 `tool_result`，流式响应有块级的开始、增量和结束事件，所以一个工具的参数收完就可以提前执行，多个工具天然可以并行。OpenAI-compatible 则是扁平的 `assistant.tool_calls` 加 `role=tool` 的消息，参数是 JSON 字符串，流式下要按 index 把分片聚合起来，结束信号是 `finish_reason=tool_calls`；它没有块级结束事件，文本和工具调用通常也不能交错。两者的差别不只是格式，而是“表达力”和“可移植性”的取舍。

Anthropic 这套的优点是类型清晰、工具调用 id 和参数都是结构化对象，文本和工具块可以交错，流式下可以按块提前执行，权限和审计也能细到 block 层；代价是绑定厂商、消息形状约束多，流式实现也更复杂。OpenAI-compatible 的优点是生态广、接入简单，GLM、豆包、Qwen、DeepSeek 等大量兼容，适合非流式或简单 Agent；代价是 JSON 字符串可能坏、需要修复，流式聚合麻烦，不同厂商在细节上还有差异。不要把两种格式直接混在 loop 里，否则换模型会污染整个运行时。

更稳妥的做法是 loop 只认内部统一的 `ModelResponse`、`ToolCall` 和 `ToolResult`，Anthropic 和 OpenAI-compatible 各自写适配器，把厂商格式归一化；工具 schema 走 API 的 `tools` 字段，system prompt 只写使用原则，不重复 schema。选型上，如果只接一家、追求最低延迟和工具表达力，选 Anthropic 的结构化 block；如果要多厂商和国内生态，选 OpenAI-compatible，但要接受解析和流式聚合的复杂度。边界在于流式提前执行只适合只读或幂等工具，有副作用的工具仍然要顺序执行并过权限门禁；否则“更快”会变成“更快地产生不可逆副作用”。
