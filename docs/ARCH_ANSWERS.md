# 架构设计题回答

> 题目要求：5 个模块，每个模块选 1 道题回答。本文把 5 篇回答放在同一个文件里。
> 写作原则：**结论先行、机制清楚、有取舍、有边界**；不堆名词，不虚构生产数据。

## 选题总览

| 模块 | 选题 | 核心结论 |
|---|---|---|
| 一、Context / Performance | Q2：200 轮压缩 | 按 token 预算分层压，保留目标/约束/待办/最近对话，摘要结构化，原文可回查 |
| 二、Memory | Q1：半个月后的召回 | 记忆分层 + 抽取写入 + 多信号召回 + 系统提示注入；不是对聊天记录做 RAG |
| 三、Task | Q1：长程任务忘目标 | 目标外置、每轮重锚定、独立审计、机器可校验的完成门禁 |
| 四、Tool / Session Runtime | Q2：busy 时新消息/异步完成 | 单写者状态机 + 事件队列；用户消息排队/安全点注入，异步结果带 id 幂等入队 |

## 模块一：Context / Performance

### Q2：一个 session 连续聊了 200 轮，context 快爆了，怎么压缩？如何保证压缩后仍然流畅？

**结论**

不要按“轮数”压，按 **token 预算** 分层压：先做无损/低成本的工具结果预算和微压缩，再做旧轮摘要；始终保留目标、硬约束、待办和最近几轮原文；摘要用固定 schema，原始旧消息落 transcript 以便回查；压缩后做连续性验收。

**1. 先量化，再决定压什么**

200 轮里 token 大头通常不是用户话，而是：

- 工具结果（文件内容、命令输出、检索片段）；
- 重复的 system prompt / 工具定义；
- 历史轮次的重复叙述；
- 模型自己的长回答。

先统计各段占比，再决定层级；否则容易把“目标/约束”先压掉。

**2. 分层压缩（从便宜到贵）**

| 层 | 做法 | 触发 | 代价 |
|---|---|---|---|
| L0 工具结果预算 | 单结果超限时头尾保留，全文落 artifacts | 每次工具返回 | 0 |
| L1 微压缩 | 合并连续小结果、去重复空行/重复报错 | 利用率中段 | 0 |
| L2 旧轮摘要 | 旧轮次压成结构化摘要，保留最近 N 轮原文 | token 超预算 | 1 次模型调用 |
| L3 归档/回查 | 原文写 transcript，需要时按需取回 | 压缩时 | 磁盘 |
| 兜底 | API 报 context 超限时 reactive compact + 重试 | 异常 | 1 次调用 |

本项目实现的是 L0 + L2 + transcript 归档；200 轮场景下建议补 L1 和 L3 的按需检索。

**3. 保留 / 丢弃**

保留：

- 当前用户消息（原文）；
- 目标、硬约束、用户偏好；
- 当前 todo / 任务状态；
- 最近 6 轮原文；
- 工具调用的 name/id/args 摘要；
- 旧轮摘要。

丢弃：

- 重复工具输出；
- 寒暄、空响应；
- 已完成的中间步骤；
- 模型的思考过程（只留结论）；
- 完整旧原文（落 transcript，不留在上下文）。

**4. 摘要 schema**

```
目标：
硬约束/用户偏好：
已确认事实：
已完成：
未完成/待确认：
重要工具结论（带来源）：
下一步：
```

固定 schema 的好处：压缩后模型知道“哪些是事实、哪些是待办”，而不是读一段散文。

**5. 如何保证压缩后仍然流畅**

- 摘要放 system prompt 的独立小节，不插入 messages，避免破坏 `tool_use/tool_result` 配对；
- 最近 6 轮原文永远保留，当前问题绝不改写；
- todo 每轮重新注入，不依赖摘要；
- 不在工具链中间压缩，只在用户轮次边界切；
- 压缩后做连续性检查：追问“当前目标是什么、有哪些约束、上一步做了什么”；
- 原始旧消息落 transcript，模型需要细节时可回查。

**6. 取舍与边界**

- 摘要会丢细节，所以只压“旧”轮次，且保留可回查原文；
- 摘要本身消耗一次模型调用，且会破坏前缀缓存；高频压缩不划算，应设置缓存热度门；
- 对法律/医疗/合同这类“逐字约束”场景，不能只靠摘要，必须保留原文引用或外部检索；
- 200 轮的真实压测需要看“约束保留率、追问正确率、压缩前后 token/成本”，不能只看摘要是否通顺。

**一句话**

> 压缩的本质不是“删旧消息”，而是 **按信息价值分层**：目标和约束不能丢，工具结果可以预算，旧过程可以摘要，原文要能回查。

## 模块二：Memory

### Q1：和聊天 Agent 熟悉半个月后，用户问了一个以前问过的问题，如何做 memory 召回更合理？

**结论**

长期记忆不是“聊天记录 RAG”，而是 **抽取后的事实、偏好和任务状态**。召回由触发条件决定：session 开始拉偏好和活跃任务，每轮按关键词/实体命中拉相关记忆，用户明确提“上次/之前”时放宽召回；排序用相关性 × 时间衰减 × 重要性，限 token，放在 system prompt 的独立小节，带来源和时间，并允许用户纠正。

**1. 记忆分层**

| 层 | 内容 | 生命周期 |
|---|---|---|
| working memory | 当前对话、当前任务 | 当前 turn |
| session memory | 会话摘要、todo | 当前 session |
| episodic memory | 过去发生的事、任务结果 | 跨 session |
| semantic memory | 稳定偏好、事实、术语 | 长期 |

“半个月后问以前问过的问题”主要查 episodic + semantic，不是把 15 天的原始聊天全塞进去。

**2. 写入：抽取而不是全存**

候选来源：

- 用户明确说“记住 / 以后都 / 我喜欢 / 我的…是”；
- 任务完成后抽取的稳定结论；
- 用户纠正过的偏好（feedback）。

写入前：

- 去重；
- 冲突检测（新旧矛盾时旧记录标 superseded）；
- 置信度 + 来源；
- 可选：提案 → 人确认 → 再写入（防止记忆污染）。

**3. 召回时机**

- session 开始：用户偏好 + 活跃任务；
- 每轮用户消息：与 query 关键词/实体命中的记忆；
- 用户明确提“上次 / 之前 / 还记得”：放宽 top-k；
- 任务开始：项目/领域事实；
- 不召回：无关、低置信度、已过期。

**4. 召回与排序**

- 关键词/实体匹配：稳定、可解释；
- 向量召回：语义相似，适合“说法不同但意思相同”；
- 时间衰减：半个月前的偏好仍然有用，但半个月前的临时任务可能已过期；
- 重要性/置信度：用户明确说的 > 模型推断的；
- 混合后 rerank，再按 token 预算截断。

**5. 放在哪**

放 **system prompt 的独立小节**，例如：

```
## 长期记忆（可能过时，当前指令优先）
- [preference, 2026-10-01] 用户偏好先给结论
- [task_state, 2026-10-20] 正在准备 Agent 笔试
```

原因：

- 记忆是背景，不是用户本轮指令；放 system 保持指令层级；
- 带时间和来源，模型/用户能判断是否过时；
- 限 token，避免挤占当前任务。

**6. 取舍与边界**

- 不把原始聊天全量做 RAG：噪声大、冲突多、成本高；
- 不把所有记忆都注入：会挤占上下文；
- 记忆可能过时：必须有时间戳和“当前指令优先”的提示；
- 记忆污染：写入前校验、冲突处理、必要时人工确认；
- 隐私：记忆是用户数据，要可查看、可删除、可关闭。

**一句话**

> 好的 memory 不是“记得多”，而是 **在正确的时机、用正确的排序、把正确的少量记忆放到正确的位置**；并且允许用户纠正和遗忘。

## 模块三：Task

### Q1：对于长程任务，大模型执行一段时间可能会忘掉目标，有哪些解决方案？各有什么优缺？

**结论**

目标遗忘的本质是 **上下文衰减 + 自我评估失真**。核心解法不是反复提醒“别忘了目标”，而是把目标外置成可检查的状态，每轮重锚定，用独立审计和机器可校验的完成门禁约束“是否真的完成”，并在关键节点 checkpoint。

**1. 失败模式**

| 失败模式 | 表现 |
|---|---|
| 目标漂移 | 做着做着变成另一个任务 |
| 上下文衰减 | 早期约束被挤出窗口 |
| 假完成 | 模型说“已完成”，但环境没变 |
| 错误滚雪球 | 一步错，后续都基于错的前提 |
| 奖励黑客 | 只做容易验证的部分，绕过难点 |

**2. 目标外置**

- **goal contract**：目标 + 验收条件 + 硬约束；
- **todo/plan**：可勾选子任务；
- **progress ledger**：每步做了什么、证据、下一步；
- **checkpoint**：关键文件/工作区快照，可回滚。

**3. 每轮重锚定**

在 system prompt 或每轮注入：

- 当前目标；
- 硬约束；
- 当前 todo；
- 上一步进展；
- 未决问题。

阶段性地重新规划，而不是一条路走到黑。

**4. 独立审计**

执行者说“做完”不算数。参考 LongHorizon-Harness 的三角色：

- Manager：只拆解/调度，不执行；
- Executor：执行，每轮新上下文；
- Auditor：只读验证环境是否真的改变。

完成必须是机器可校验的契约，例如：

```
Status: complete
Integrity: clean
Contract audit: aligned
```

三条不同时满足，不能宣布完成。证据必须来自环境，不能只来自执行者自述。

**5. 防止过度怀疑和层层加码**

两个反向约束同样重要：

- Manager 添加的、不是基于原始请求的谨慎，不能创造新的阻塞要求；
- 缺少完整执行记录不等于篡改；不可观察的过去不必为了证明而重做。

否则任务会陷入“永远在验证、永远完不成”。

**6. 取舍与边界**

- 审计会增加成本/延迟；只在高风险节点或关键完成点做；
- 门禁太严会阻塞任务；门禁必须可解释、可修订；
- 子任务用 fresh context 能防污染，但会丢上下文；用 artifacts/progress 传递结果；
- 对开放式任务，“完成”本身难以定义；需要把验收条件写具体。

**一句话**

> 长任务不忘目标的可靠办法是 **把目标变成外部状态，把完成变成可验证的事实**；不是让模型“更努力地记住”。

## 模块四：Tool / Session Runtime

### Q2：如果 session state 为 busy，此时用户又发来新消息，或者异步工具完成事件也到达，runtime 应该如何处理？

**结论**

把 session 做成 **单写者状态机 + 事件队列**。busy 时用户新消息不直接并发进 loop，而是入队，在安全点决定“注入 / 排队 / 取消”；异步工具完成作为带 `tool_call_id` 的事件进入同一队列，做幂等匹配。所有状态转换可恢复、可去重。

**1. 状态与事件**

```
IDLE --USER_MSG--> RUNNING_LLM --TOOL_CALL(sync)--> RUNNING_TOOL --RESULT--> RUNNING_LLM
  ▲                    │
  │                    └--ASYNC_CALL--> WAITING_ASYNC --TOOL_COMPLETE--> RUNNING_LLM
  │                                          │
  └──────────── CANCEL / ERROR ◀─────────────┘
```

事件：`USER_MESSAGE`、`LLM_RESPONSE`、`TOOL_COMPLETE`、`CANCEL`、`TIMEOUT`。

**2. busy 时用户新消息**

| 策略 | 体验 | 风险 |
|---|---|---|
| 排队 | 简单、顺序稳定 | 延迟 |
| 安全点注入/steer | 用户能纠偏 | 实现复杂，要定义安全点 |
| 取消当前任务 | 响应快 | 已产生的副作用要处理 |
| 直接拒绝 | 简单 | 体验差 |

推荐：**默认排队 + 安全点 steer + 显式 stop 取消**；给用户 ack，不要静默丢弃。

安全点：一轮 LLM 返回后、工具调用之间、工具结果回填后；不要在工具执行中间插消息。

**3. 异步工具完成**

事件至少带：

```json
{"type":"tool_complete","session_id":"...","tool_call_id":"...","result":"...","ts":"..."}
```

处理：

- 先查 pending 表，匹配 `tool_call_id` 才接收；
- 重复事件幂等丢弃；
- session busy → 入同一队列，当前步结束后处理；
- session 已取消 → 标记 stale，存结果但不回灌；
- 结果持久化，崩溃后可恢复；
- 有超时和重试上限。

**4. 一致性与恢复**

- 每个 session 一个单写者 actor/queue，避免两个 loop 并发写历史；
- 事件有单调序号；
- 状态转换带版本号/乐观锁；
- 所有写操作幂等；
- 事件日志 + pending tool 表支持重启恢复；
- 队列有上限和背压，超限通知用户。

**5. 取舍与边界**

- 队列简单但延迟；steer 体验好但状态机复杂；
- 取消要处理“已经产生的副作用”（例如已经发出的请求、已经写的文件）；
- 异步结果可能晚到很久，不能让 session 永远 busy；要有超时和“稍后通知”；
- 多进程/多实例部署需要分布式锁或单写者路由，内存队列不够。

**一句话**

> busy 不是“拒绝新事件”，而是 **把事件放进同一个有序队列，由单写者在安全点串行决策**；异步完成也必须带 id、幂等、可恢复。

## 模块五：Runtime 对比

### Q1：Claude Code 的工具输出方式和国内 GLM / 豆包等 OpenAI-compatible function calling 有什么不同？各自优缺点？

**结论**

Anthropic/Claude Code 把工具调用和结果做成 **结构化 content block**：assistant 里是 `tool_use`，user 里回 `tool_result`，流式有块级事件，天然支持并行和“参数收完就执行”。OpenAI-compatible 是 **扁平的 `tool_calls` + `role=tool` 消息**，参数是 JSON 字符串，流式按 index 聚合，结束信号是 `finish_reason=tool_calls`。前者表达力强、类型清晰，但绑定厂商；后者生态广、接入简单，但解析和流式聚合更脏。

**1. 协议对比**

| 维度 | Anthropic / Claude Code | OpenAI-compatible |
|---|---|---|
| 工具声明 | `tools` + `input_schema` | `tools` + `function.parameters` |
| 模型输出 | content blocks：`text` / `tool_use` | `assistant.tool_calls[]`，`arguments` 是 JSON 字符串 |
| 工具结果 | user 消息里的 `tool_result` block | `role: "tool"` + `tool_call_id` |
| 流式 | 块级事件（start/delta/stop） | delta 分片，按 index 聚合 |
| 并行工具 | 天然多 block | 多 tool_calls，按 index/顺序 |
| 结束信号 | `stop_reason: tool_use` | `finish_reason: tool_calls` |
| 多模态/交错 | 文本和工具块可交错 | 通常分离 |

**2. Claude Code 这样设计的优点**

- 类型清晰：工具名、id、参数是结构化对象，不靠字符串解析；
- 可交错：文本和工具调用可以在同一个 assistant 消息里；
- 流式友好：`content_block_stop` 表示某个工具参数收完，可以提前执行，把工具时间藏进模型生成窗口；
- 并行自然：多个 `tool_use` block 可以并行/提前执行；
- 权限/审计可以在 block 层做，粒度细。

缺点：

- 绑定 Anthropic 协议，换厂商要改；
- 消息形状约束多（`tool_result` 必须配对、角色顺序等）；
- 流式实现比非流式复杂。

**3. OpenAI-compatible 这样设计的优点**

- 生态广：GLM、豆包、Qwen、DeepSeek 等大量兼容；
- 协议简单：`tool_calls` + `role=tool`，接入成本低；
- 适合非流式/简单 Agent。

缺点：

- `arguments` 是 JSON 字符串，可能坏、需要修复；
- 流式下多个工具调用的分片交错，要按 index 聚合，且没有块级结束事件；
- 文本和工具调用通常不能交错；
- 不同厂商在细节上仍有差异。

**4. 我们项目的做法**

- loop 只认内部 `ModelResponse` / `ToolCall` / `ToolResult`；
- Anthropic 适配器把 `tool_use` / `tool_result` 转成内部结构；
- 工具 schema 走 API `tools` 字段，system prompt 只写使用原则；
- 如果以后接 OpenAI-compatible，只加适配器，不改 loop。

**5. 取舍与边界**

- 如果只接一家、追求最低延迟和工具表达力，选 Anthropic 结构化 block；
- 如果要多厂商/国内生态，选 OpenAI-compatible，但要接受 JSON 字符串解析和流式聚合的复杂度；
- 不要直接在 loop 里写厂商格式，否则换模型会污染整个运行时；
- 流式提前执行只适合只读/幂等工具；有副作用的工具要顺序、要权限门禁。

**一句话**

> 两者的核心差异不是“谁更先进”，而是 **表达力 vs 可移植性**：Anthropic 用结构化 block 换表达力和流式优化，OpenAI-compatible 用扁平消息换生态和接入简单。
